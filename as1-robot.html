為什麼 L2 Arm 的矩陣要乘上 Mtorso 和 Marm1？

L2 Arm 的 local 矩陣只描述「相對於 L1 Arm 的手肘」的位置與旋轉。往左乘 Marm1 轉到 torso 空間，再乘 Mtorso 轉到 world。所以 torso 移動 / 旋轉時整條手臂跟著動。

畫部位時的 scale 為什麼不能傳給子節點？

scale 只是把單位大小的 Cube / Capsule 拉成部位的形狀。若傳下去，子節點的平移量和形狀都會被父的 scale 拉伸（例如手臂被拉長兩倍，手肘的位置也被拉遠兩倍、前臂也變形）。做法：Mjoint 往下傳，畫自己時另外乘 scale。在 5. 勾「錯誤：scale 傳給子節點」可以看到效果。

T * R 和 R * T 差在哪？手臂要繞肩膀轉該用哪個？

關鍵：矩陣乘在頂點上時，是從右邊開始套用。所以 T * R * v 是「先 R、後 T」，R * T * v 是「先 T、後 R」。

用手臂當例子（T = 移到肩膀、R = 旋轉 30°）：

寫法實際順序結果
T * R① 手臂還在原點時先轉 30°
② 再把轉好的手臂搬到肩膀		✓ 手臂在肩膀上，以肩膀為支點擺動
R * T① 先把手臂搬到肩膀
② 再繞「原點（身體中心）」轉 30°		✗ 整隻手臂繞著身體中心公轉，離開肩膀

所以繞肩膀轉要用 T * R。因為 rotate 一定是繞「目前座標系的原點」轉，要先在原點轉好再移過去。

完整的手臂矩陣（對應 main.cpp 的 jointMatrix + drawPart）：

Mjoint = Mtorso * T(肩膀位置) * R(角度)        // 關節矩陣，會傳給前臂
Mdraw  = Mjoint * T(0, -半長, 0) * S(粗, 半長, 粗)   // 只用來畫上臂

最後多乘 T(0, -半長, 0)：Capsule 的中心在原點，往下移半個長度，手臂的頂端才會剛好接在肩膀上，旋轉時以頂端為支點。可在 5. 階層模型互動 選「R·T 順序錯」看錯誤效果。

glm::rotate 的角度單位？

弧度（radian）。用角度要 glm::radians(30.0f)。

VAO 存了什麼？為什麼每個 mesh 一個 VAO？

VAO 記錄 attribute 設定（哪個 location 從哪個 VBO、什麼格式、stride、offset 讀）以及 element buffer 綁定。每個 mesh 一個 VAO，畫的時候 glBindVertexArray 一行就切換全部設定。

uniform 和 vertex attribute 差在哪？

attribute 每個頂點不同（position、uv），從 VBO 讀；uniform 在一次 draw call 內所有頂點相同（M、V、P、顏色、sampler），用 glUniform* 設定，要先 glUseProgram。

沒開 depth test 會怎樣？為什麼每幀要 clear depth？

沒開：後畫的永遠蓋掉先畫的，背後的腿可能畫在身體前面。不 clear depth：上一幀的深度殘留，新畫面大部分 fragment 被判定「比較遠」而丟掉 → 畫面殘缺或全空。

stbi_set_flip_vertically_on_load(true) 為什麼需要？

圖檔第一列是影像最上面，OpenGL texture 的 v=0 是最下面。不翻轉的話貼圖上下顛倒。

VS 輸出的 gl_Position 在哪個空間？之後誰做 perspective divide？

Clip space。之後 fixed function 的 primitive assembly / clipping 做除以 w 得到 NDC，再經 viewport transform 到 screen。

動畫為什麼用 glfwGetTime() 的時間差，而不是每幀 +1？

每幀 +1 的速度跟 FPS 綁在一起，換台電腦（或關掉 vsync）動畫速度就不同。用經過的時間累加，任何 FPS 下速度都一樣；暫停 = 不累加時間。

選取部位的 world matrix（2D 齊次 3×3）

對應到 3D 程式

每個部位都會用到兩種矩陣，分清楚就不會錯：

矩陣內容用途
關節矩陣父的關節矩陣 × T(關節位置) × R(關節角度)往下傳給子部位當 parent
繪製矩陣關節矩陣 × T(往下移半截) × S(部位大小)只拿來畫自己，不往下傳

scale 只出現在繪製矩陣，所以不會傳給子部位；這就是「scale 不能傳給子節點」的做法。

以下用作業程式的實際數字（Torso → 左上臂 → 左前臂），把 main.cpp 的 jointMatrix / drawPart 展開成 glm 寫法：

// ① Torso（root）：沒有 parent，從單位矩陣開始
glm::mat4 torso = glm::mat4(1.0f);
torso = glm::translate(torso, robotPos + glm::vec3(0, 2.26f, 0));   // 放到世界中的位置（WASD 控制）
torso = glm::rotate(torso, robotYaw, glm::vec3(0, 1, 0));            // 整隻轉向（QE / 滑鼠控制）
//   （main.cpp 這裡還會再乘上動畫的身體傾斜 p.torso，這裡省略）
//   畫身體：Cube 邊長 1 → 縮放成 1.1 × 1.2 × 0.6
drawPart(cube, glm::scale(torso, glm::vec3(1.1f, 1.2f, 0.6f)), BODY_COLOR);

// ② 左上臂（L1 Arm）：parent = torso 的「關節矩陣」
glm::mat4 arm1 = glm::translate(torso, glm::vec3(-0.7f, 0.45f, 0));  // 關節位置 = 肩膀（相對於 torso 中心）
arm1 = glm::rotate(arm1, angleArm1, glm::vec3(1, 0, 0));             // 繞肩膀前後擺（繞 x 軸）
//   畫上臂：長 0.6。Capsule 高 2、中心在原點 → y 縮放 0.3 變成高 0.6，
//   再往下移 0.3（半個長度），頂端才剛好接在肩膀上
glm::mat4 arm1Draw = glm::translate(arm1, glm::vec3(0, -0.3f, 0));
arm1Draw = glm::scale(arm1Draw, glm::vec3(0.22f, 0.3f, 0.22f));
drawPart(capsule, arm1Draw, ARM_COLOR);

// ③ 左前臂（L2 Arm）：parent = arm1（關節矩陣），不是 arm1Draw！
glm::mat4 arm2 = glm::translate(arm1, glm::vec3(0, -0.6f, 0));      // 關節位置 = 手肘 = 上臂末端（往下一整個長度）
arm2 = glm::rotate(arm2, angleArm2, glm::vec3(1, 0, 0));             // 繞手肘彎曲
glm::mat4 arm2Draw = glm::translate(arm2, glm::vec3(0, -0.3f, 0));
arm2Draw = glm::scale(arm2Draw, glm::vec3(0.198f, 0.3f, 0.198f));   // 比上臂細一點（0.22 × 0.9）
drawPart(capsule, arm2Draw, ARM_COLOR);
變數等於（矩陣乘法）說明
torsoT(位置) · Ry(yaw)= 講義的 Mtorso
arm1Mtorso · T(肩膀) · R(angleArm1)= Mtorso · Marm1
arm2Mtorso · Marm1 · T(手肘) · R(angleArm2)= Mtorso · Marm1 · Marm2
arm2Drawarm2 · T(0, −0.3, 0) · S(0.198, 0.3, 0.198)只用來畫前臂
  • 為什麼一路寫下來就是矩陣連乘？glm::translate(m, v)、glm::rotate(m, …)、glm::scale(m, …) 都是「m 乘上新矩陣」（新矩陣乘在右邊）。所以從 torso 開始一行一行往下寫，結果自動是 Mtorso · Marm1 · Marm2。
  • 為什麼 torso 一動整隻手跟著動？arm1、arm2 都是從 torso 乘出來的，torso 改了，它們全部跟著改。
  • 常見錯誤：把 arm1Draw（含 scale）當成 arm2 的 parent → 前臂被上臂的 scale 壓扁、手肘位置跑掉。在上面互動圖選「scale 傳給子節點」可以看到。
  • 和 main.cpp 的對應：jointMatrix(parent, 位置, 角度) = 上面的 translate + rotate；drawPart(mesh, joint, offset, size, …) = 上面的 translate(offset) + scale(size) + 畫。
  • 也可以用 std::stack<glm::mat4>：進入子部位前 push 目前矩陣、畫完 pop 回來，概念相同；本作業直接用變數保存各關節矩陣，比較好讀。

#define TINYOBJLOADER_IMPLEMENTATION
#include "tiny_obj_loader.h"

struct Mesh { GLuint vao = 0, vbo = 0; GLsizei count = 0; };

Mesh loadObj(const char* path)
{
	tinyobj::attrib_t attrib;
	std::vector<tinyobj::shape_t> shapes;
	std::vector<tinyobj::material_t> materials;
	std::string warn, err;
	if (!tinyobj::LoadObj(&attrib, &shapes, &materials, &warn, &err, path)) {
		fprintf(stderr, "LoadObj failed: %s %s\n", path, err.c_str());
		return {};
	}
	std::vector<float> data;                       // interleaved: pos(3) uv(2)
	for (const auto& s : shapes)
		for (const auto& idx : s.mesh.indices) {      // 每個 index = 三角形的一個角
			for (int k = 0; k < 3; ++k) data.push_back(attrib.vertices[3 * idx.vertex_index + k]);
			for (int k = 0; k < 2; ++k) data.push_back(attrib.texcoords[2 * idx.texcoord_index + k]);
		}
	Mesh m;
	m.count = (GLsizei)(data.size() / 5);
	glGenVertexArrays(1, &m.vao);
	glBindVertexArray(m.vao);
	glGenBuffers(1, &m.vbo);
	glBindBuffer(GL_ARRAY_BUFFER, m.vbo);
	glBufferData(GL_ARRAY_BUFFER, data.size() * sizeof(float), data.data(), GL_STATIC_DRAW);
	GLsizei stride = 5 * sizeof(float);
	glVertexAttribPointer(0, 3, GL_FLOAT, GL_FALSE, stride, (void*)0);                     // position
	glVertexAttribPointer(1, 2, GL_FLOAT, GL_FALSE, stride, (void*)(3 * sizeof(float)));   // uv
	glEnableVertexAttribArray(0);
	glEnableVertexAttribArray(1);
	glBindVertexArray(0);
	return m;
}
  • OBJ 的 v / vt 各自有獨立 index，所以這裡把每個角展開成一筆完整頂點、用 glDrawArrays。沒做光照就不需要 normal（vn）。換成別的 OBJ 要先檢查 texcoord_index 是否 ≥ 0。

初始化與主迴圈

i1. #include <glad/glad.h> 為什麼一定要在 GLFW 之前？（main.cpp:16）

glad.h 自己宣告了全部 OpenGL 型別與函式指標，並會檢查「OpenGL header 是否已被 include」。GLFW 的 header 預設會 include 系統的 GL/gl.h；若先 include GLFW，glad 會報 OpenGL header already included。先 include glad，GLFW 偵測到就不再 include 系統 header。

i2. gladLoadGLLoader 為什麼要在 glfwMakeContextCurrent 之後？（main.cpp:510–518）

GLAD 透過 glfwGetProcAddress 向目前的 OpenGL context 查詢每個 gl* 函式的位址。還沒有 current context 時查不到，函式指標都是 null，之後呼叫任何 gl*（例如 loadObj 裡的 glGenVertexArrays）就 crash。所以載入資源也必須在 GLAD 之後。

i3. 四行 glfwWindowHint 各在做什麼？拿掉 FORWARD_COMPAT 會怎樣？（main.cpp:500–503）

要求 OpenGL 4.1、core profile（沒有 fixed function）、forward compatible（移除所有 deprecated 功能）。macOS 要建立 3.2 以上的 core context 必須設 forward compat，拿掉在 Mac 上 glfwCreateWindow 會失敗回傳 null（程式 return 1）；Linux / Windows 通常沒差。版本 4.1 是因為 macOS 最高只支援 4.1。

i4. glfwSwapInterval(1) 是什麼？改成 0 動畫會變快嗎？（main.cpp:511）

vsync：swap 時等一次螢幕垂直同步，FPS 被限制在螢幕更新率（例如 60 Hz）。改 0 FPS 會變很高，但動畫不會變快：animTime += dt、移動量 2.0f * dt 都乘上經過的實際時間，與 FPS 無關。

i5. 主迴圈每一幀依序做了什麼？為什麼 ImGui 最後才 Render？（main.cpp:552–585）

poll events → 算 dt、累加 animTime → processInput → ImGui NewFrame ×3 + on_gui()（只建立 UI 資料，還沒畫）→ viewport → on_display 畫機器人 → ImGui::Render + RenderDrawData → swap。ImGui 最後畫才會蓋在場景上面；它的 backend 畫的時候會暫時關 depth test，畫完再還原。

i6. 為什麼要 glfwSwapBuffers？只有一個 buffer 會怎樣？

Double buffering：所有繪製畫在 back buffer，畫完整張再跟 front buffer（螢幕上顯示的）交換。只有一個 buffer 的話，使用者會看到畫到一半的畫面（閃爍、撕裂）。

i7. glfwPollEvents 做什麼？你的 cursor_pos_callback 是什麼時候被呼叫的？

處理作業系統累積的視窗事件（鍵盤、滑鼠、resize…），並在這個函式裡面同步呼叫已註冊的 callback。所以 mouse_button_callback / cursor_pos_callback 都在 main.cpp:554 那一行執行期間被呼叫（先經過 ImGui 的 callback，再串到你的）。

i8. 陷阱 視窗最小化一段時間再還原，動畫會怎樣？（main.cpp:555–566）

最小化時 continue 跳過了整段，包括 lastTime = now。還原後第一幀 dt = 整段最小化的時間 → animTime 一次跳很多（動畫跳格）；如果當時按住 WASD，機器人會瞬間移很遠。修法：在 continue 前更新 lastTime = glfwGetTime()，或把 dt 夾在上限（如 std::min(dt, 0.1f)）。

i9. 為什麼 glfwSetErrorCallback 在 glfwInit 之前？（main.cpp:494）

它是少數可以在 init 前呼叫的 GLFW 函式。先設好，glfwInit 本身失敗（例如沒有顯示器、缺 X11 / Wayland）時也能印出原因。

Shader 與 GLSL

s1. VS 的 layout(location = 0) in vec3 aPos 跟 C++ 哪一行對應？

main.cpp:190 的 glVertexAttribPointer(0, 3, GL_FLOAT, …) 和 glEnableVertexAttribArray(0)：attribute 0、3 個 float。uv 是 location 1、2 個 float（main.cpp:191）。編號不一致 VS 就讀到錯的資料。

s2. uP * uV * uM * vec4(aPos, 1.0)：為什麼是這個順序？為什麼 w = 1.0？

矩陣從右邊開始作用在頂點：先 M（model → world）、再 V（world → view）、最後 P（view → clip）。寫成 uM * uV * uP 就錯。w = 1 表示「點」，4×4 矩陣最後一欄的平移才會作用；w = 0 是方向向量，不受平移影響。

s3. gl_Position 在哪個座標空間？之後到 FS 之前發生了什麼？

Clip space。之後 fixed function：primitive assembly → clipping → perspective divide（÷w 得 NDC）→ viewport transform（到螢幕像素）→ rasterization（產生 fragment，內插 vUV）→ FS → depth test → 寫入 framebuffer。

s4. VS 的 out vec2 vUV 跟 FS 的 in vec2 vUV 怎麼連起來？FS 拿到的值是哪個頂點的？

link 時依名字和型別配對。FS 拿到的不是任何一個頂點的值，而是 rasterizer 依 fragment 在三角形內的位置，用三個頂點的 vUV 做（透視校正的）重心內插的結果。

s5. uniform sampler2D uTex 裡存的是什麼？為什麼 C++ 用 glUniform1i(locTex, 0)？

存的是 texture unit 編號，不是 texture id。glActiveTexture(GL_TEXTURE0) 選 unit 0、glBindTexture 把 chestTex 綁到 unit 0、glUniform1i(locTex, 0) 告訴 sampler 去 unit 0 讀（main.cpp:421–423）。

s6. uniform bool uUseTex 為什麼用 glUniform1i 設定？

GLSL 的 bool uniform 沒有專用的 glUniform 函式，用 glUniform1i（或 1f）設定，0 = false、非 0 = true（main.cpp:338）。

s7. 為什麼每次 drawPart 都要重設 uColor 和 uUseTex？

uniform 的值存在 program 裡，設了就一直保留到下次改。如果只在胸口板設 uUseTex = 1 而不在其他部位設回 0，之後畫的所有部位都會變成貼圖。每次畫都設一次最保險。

s8. 為什麼 P、V、M 分開傳，不在 CPU 先乘好傳一個 MVP？

兩種都可以。分開傳比較好讀、P / V 每幀只設一次。代價是 VS 對每個頂點都做兩次 4×4 矩陣乘法（每幀約 5 萬個頂點），在 CPU 對 29 個部位各乘一次 MVP 會更省；本作業規模差異可忽略。

s9. 為什麼 shader 開頭是 #version 410 core？

對應 context 的 OpenGL 4.1 core（GLSL 4.10）。版本寫太高在 macOS 編不過；ImGui backend 也用同一版（glsl_version = "#version 410"，main.cpp:499）。

Shader 編譯 / 連結

c1. 說明 createProgram 的完整流程。（main.cpp:124–147）

兩次 compileShader（create → source → compile → 查 GL_COMPILE_STATUS，失敗印 info log）→ glCreateProgram → 兩次 glAttachShader → glLinkProgram → 查 GL_LINK_STATUS → glDeleteShader 兩個 shader 物件 → 回傳 program。

c2. link 完就 glDeleteShader，program 不會壞掉嗎？

不會。link 後 program 已經有自己的可執行碼。shader 物件仍 attach 在 program 上時，delete 只是標記刪除，等 detach 或 program 被刪時才真的釋放。

c3. 在錯的目錄執行程式會發生什麼？從程式哪裡看得出來？

readFile 開檔失敗印 Cannot open shaders/... (請在專案根目錄執行)，回傳空字串 → 編譯空 shader 失敗 → link 失敗；loadObj 印 LoadObj failed、count = 0；畫面只剩背景色 + ImGui。路徑是相對於工作目錄，不是執行檔位置。

c4. 陷阱 compileShader 失敗時程式會停下來嗎？

不會，只印錯誤，仍回傳 shader 繼續 link。link 失敗的 program 在 glUseProgram 時產生 GL_INVALID_OPERATION，之後什麼都畫不出來，但程式不會 crash。要更嚴謹可以失敗時回傳 0 並結束程式。

c5. 為什麼 uniform location 在 link 後取一次存成全域變數？什麼時候會拿到 −1？

glGetUniformLocation 是用字串查表，每幀查很浪費；location 在 link 後就固定，存起來重複用（同講義 Spinning Cube）。−1：名字打錯，或該 uniform 在 shader 裡沒被用到、被 compiler 優化掉。對 −1 呼叫 glUniform* 會被靜默忽略，不報錯。

c6. glShaderSource(shader, 1, &src, nullptr) 的 4 個參數？src 指向的字串會不會先被釋放？

shader、字串數量 1、字串指標陣列、長度陣列（nullptr = 以 \0 結尾）。src = source.c_str()，source 是同一個函式的區域變數，活到函式結束；而且 glShaderSource 會複製字串，呼叫完就不再需要它。

OBJ / VAO / VBO

m1. 為什麼 loadObj 要把每個角展開成一筆頂點，不用 EBO + glDrawElements？

OBJ 的 face 對 position、uv 各有獨立的 index（f 1/3/1），OpenGL 一個頂點只能有一個 index。直接展開最簡單，用 glDrawArrays 畫。代價是重複頂點：Cube 只有 24 個不同頂點卻存了 36 筆。要用 EBO 得先把相同的 (v, vt) 組合去重。

m2. attrib.vertices[3 * idx.vertex_index + k] 為什麼乘 3？texcoord 為什麼乘 2？

tinyobj 把所有 position 存成一條扁平的 float 陣列 [x0 y0 z0 x1 y1 z1 …]，第 i 個頂點從 3i 開始；uv 每個 2 個 float，所以 2i。

m3. idx.texcoord_index >= 0 的判斷是為了什麼？（main.cpp:174）

OBJ 的面若沒有 vt（如 f 1//1），tinyobj 的 texcoord_index 是 −1，直接拿來當 index 會讀越界。這裡補 0。作業的 4 個 OBJ 都有 vt，但換 OBJ 時就派得上用場。

m4. 算出 stride 和 uv 的 offset。為什麼 offset 要寫成 (void*)？

每頂點 5 float = 20 bytes（stride）；position offset 0、uv offset 3 * sizeof(float) = 12 bytes。最後一個參數是「目前綁定的 GL_ARRAY_BUFFER 裡的 byte offset」，因為舊 API 的型別是指標，所以要轉成 void*。

m5. mesh.count 存的是什麼？Cube 是多少？為什麼？

頂點數（data.size() / 5），不是三角形數。Cube 12 個三角形 × 3 = 36。glDrawArrays(GL_TRIANGLES, 0, count) 的第三個參數就是頂點數。若誤傳 count / 3，只會畫出前 1/3 的三角形。

m6. VAO 記住了什麼？GL_ARRAY_BUFFER 的綁定有記在 VAO 嗎？

VAO 記錄每個 attribute 的 enable 狀態與格式（size、type、stride、offset），以及呼叫 glVertexAttribPointer 當下綁定的 VBO；也記 GL_ELEMENT_ARRAY_BUFFER 綁定。GL_ARRAY_BUFFER 這個綁定點本身不存在 VAO 裡，是透過 glVertexAttribPointer 間接記住。所以畫的時候只要 glBindVertexArray，不用再綁 VBO（main.cpp:340）。

m7. 最後的 glBindVertexArray(0) 有什麼用？（main.cpp:195）

解除綁定，避免之後別的程式碼（例如下一次 loadObj 之前、或 ImGui）意外修改到這個 VAO 的設定。不解除也能跑，是防呆習慣。

m8. 忘了 glEnableVertexAttribArray(1) 會怎樣？忘了 0 呢？

attribute 沒啟用時，VS 讀到的是常數預設值（(0,0,0,1)）。忘了 1：所有頂點 uv = (0,0)，胸口板變成單一顏色（貼圖左下角的顏色），純色部位不受影響。忘了 0：所有頂點位置都是原點，三角形退化，什麼都看不到。

m9. GL_STATIC_DRAW 是什麼意思？

給 driver 的使用提示：資料上傳一次、畫很多次、不會再改。driver 可能放到 GPU 記憶體。只是提示，用錯不會錯誤，只影響效能。

m10. OBJ 裡有 normal（vn），為什麼沒讀？

本作業沒有光照，FS 只用純色或貼圖，用不到 normal。要做光照時才加第三個 attribute（stride 變 8 float），並在 VS 用 normal matrix 轉換。

m11. 為什麼不需要自己把四邊形切成三角形？

tinyobj::LoadObj 的 triangulate 參數預設為 true，會自動把多邊形切成三角形；而且這幾個 OBJ 本來就全是三角形面。

Texture

t1. stbi_set_flip_vertically_on_load(true) 為什麼需要？

圖檔第一列是影像最上面，OpenGL texture 的 v = 0 在最下面。不翻轉貼圖會上下顛倒。

t2. stbi_load(…, 4) 最後的 4 是什麼？nailong.png 是 RGB，為什麼還能用 GL_RGBA？

req_comp = 4：不管原圖幾個 channel，都轉成 RGBA 回傳（缺的 alpha 補 255）。channels 變數拿到的是原圖的 3，但 data 已是 4 channel，所以 glTexImage2D 用 GL_RGBA 正確。好處：不用處理 RGB 寬度不是 4 的倍數時的 GL_UNPACK_ALIGNMENT 問題。

t3. glTexImage2D 裡 GL_RGBA8 跟 GL_RGBA 差在哪？

第 3 個參數 GL_RGBA8 是 internal format：GPU 上怎麼存（每 channel 8 bit）。第 7、8 個參數 GL_RGBA, GL_UNSIGNED_BYTE 描述你傳進來的 CPU 資料格式。

t4. 如果拿掉 glGenerateMipmap，其他不變，會怎樣？

MIN_FILTER 設成 GL_LINEAR_MIPMAP_LINEAR 需要完整的 mipmap 鏈；沒有 mipmap 時 texture 是 incomplete，取樣結果是黑色 → 胸口板全黑。另一種修法是把 MIN_FILTER 改成 GL_LINEAR。

t5. MIN_FILTER 和 MAG_FILTER 什麼時候各自生效？

MAG：貼圖被放大（一個 texel 蓋多個 pixel，鏡頭靠近）。MIN：貼圖被縮小（多個 texel 擠進一個 pixel，遠處）。LINEAR_MIPMAP_LINEAR = 在兩層 mipmap 各做雙線性再內插（trilinear）。

t6. 為什麼 glTexImage2D 之後就能 stbi_image_free？

glTexImage2D 會把資料複製給 OpenGL（GPU），之後 CPU 端的記憶體就用不到了。

t7. 陷阱 胸口板呼叫 drawPart 時傳了 METAL_COLOR，這個顏色有用到嗎？（main.cpp:376）

沒有。textured = true → uUseTex = 1 → FS 直接輸出 texture(uTex, vUV)，uColor 被忽略。若想讓貼圖帶色調，可改成 texture(uTex, vUV) * vec4(uColor, 1.0)。

t8. 胸口板是一個壓扁的 Cube，6 個面都有貼圖嗎？為什麼放在 z = 0.31，不是 0.3？

6 個面都有（Cube.obj 每個面 uv 都是 0–1），側面只是很薄看不到。torso 前表面在 z = 0.6 / 2 = 0.3；板子厚 0.04、中心 0.31 → 範圍 0.29–0.33，前表面突出 torso 0.03。如果剛好和 torso 前表面重疊在同一深度，會發生 z-fighting（兩個面搶深度、閃爍）。

t9. wrap mode 沒設定，預設是什麼？會影響這個作業嗎？

預設 GL_REPEAT。Cube 的 uv 都在 0–1，所以不影響；uv 超出 0–1 時才看得出差別（重複 vs CLAMP_TO_EDGE 拉邊）。

相機與 depth

p1. glm::perspective(glm::radians(45.0f), aspect, 0.1f, 100.0f) 四個參數？（main.cpp:412）

垂直視角 fovy（弧度）、寬高比、near、far。只有 near–far 之間、視錐內的東西會被畫。

p2. 為什麼 aspect 用 std::max(height, 1)？為什麼用 framebuffer size 而不是 window size？

視窗高度可能是 0（極端縮小），除以 0 得到 inf / NaN 的投影矩陣。HiDPI 螢幕上 window size（screen 座標）和 framebuffer size（實際像素）不同，glViewport 要的是像素，所以兩者都用 glfwGetFramebufferSize 的值（main.cpp:576–579）。

p3. glm::lookAt(eye, center, up) 在你的程式裡相機在哪、看哪？

eye = (0, 3.2, 9)：機器人前上方；center = (0, 2.5, 0)：機器人胸口附近；up = +y。相機固定不動，機器人面向 +z，所以預設看到機器人正面。

p4. near 改成 0.0001 或 0 會怎樣？

depth buffer 精度在 near 附近最集中，near 太小 → 遠處物體深度幾乎相同 → z-fighting。near = 0 時投影矩陣退化，深度全部錯。

p5. 沒開 depth test 會怎樣？為什麼每幀都要清 depth buffer？

沒開：後畫的永遠蓋掉先畫的（例如後畫的腿蓋在身體前面）。不清：上一幀的深度殘留，這一幀大部分 fragment 被判定「比較遠」而丟掉 → 畫面殘缺。預設比較函式是 GL_LESS。

p6. glEnable(GL_DEPTH_TEST) 放在 on_display 每幀呼叫，有必要嗎？

不是必要。ImGui 的 OpenGL3 backend 畫 UI 時會關 depth test，但畫完會還原原本狀態，所以在初始化時開一次也行。每幀開一次成本極低、比較保險。

p7. depth buffer 是誰建立的？你有寫程式建立嗎？

沒有。GLFW 建立視窗時的 default framebuffer 預設就有 24-bit depth buffer（GLFW_DEPTH_BITS 預設 24）。

p8. 你有開 back-face culling 嗎？開了會有什麼差別？

沒有，所以每個三角形正反面都會畫。開 glEnable(GL_CULL_FACE) 會省掉背向相機的三角形（約一半），前提是 OBJ 的三角形都是逆時針（CCW）排列；畫面看起來應該一樣。

矩陣與階層

h1. 說明 jointMatrix 的乘法順序，以及套用在頂點上的實際順序。（main.cpp:319–326）

m = parent · T(position) · Ry · Rx · Rz。作用在頂點時從右往左：先繞 z、再繞 x、再繞 y（都在關節自己的座標系、以關節為支點），再移到關節位置，最後套 parent 轉到父的座標系。

h2. glm::translate(m, v) 是 m · T 還是 T · m？為什麼這很重要？

m · T（新矩陣乘在右邊）。所以從 torso 開始一行一行 translate / rotate 下去，結果自動是 Mtorso · Marm1 · Marm2，子部位的變換在父的座標系裡進行。

h3. drawPart 為什麼是先 translate 再 scale（T · S）？反過來呢？

T · S 作用在頂點是先縮放、再平移，offset 是真正的距離。S · T 的話 offset 也會被縮放：例如上臂 offset y = −0.3、scale y = 0.3，實際只移 −0.09，手臂頂端就不會接在肩膀上。

h4. 為什麼 scale 不會傳給子部位？指出程式哪裡保證了這件事。

drawPart 的 model 是區域變數，含 scale，只拿來設 uM 和畫自己；往下傳的是 jointMatrix 的回傳值（seg1、seg2、torso、head），裡面只有 T 和 R。

h5. 上臂為什麼是 offset = (0, -len/2, 0)、size = (thick, len/2, thick)？（main.cpp:353）

Capsule.obj 高 2（y ∈ [−1, 1]）、中心在原點。y scale = len / 2 → 高度變 len；再往下移 len / 2 → 頂端在關節（y = 0）、底端在 y = −len。這樣旋轉時以頂端（肩膀）為支點。

h6. 前臂（seg2）的 parent 是誰？為什麼關節位置是 (0, -len, 0)？

parent 是 seg1（上臂的關節矩陣，不含 scale）。在 seg1 的座標系裡上臂從 y = 0 延伸到 y = −len，所以手肘在 (0, −len, 0)。上臂一轉，seg1 改變，前臂自動跟著。

h7. 寫出畫「左前臂」時 VS 實際用到的完整矩陣。

P · V · T(robotPos + (0, 2.26 + bodyY, 0)) · Ry(robotYaw) · R(p.torso) · T(−0.7, 0.45, 0) · R(p.lArm1) · T(0, −0.6, 0) · R(p.lArm2) · T(0, −0.3, 0) · S(0.198, 0.3, 0.198)。前面到 R(p.lArm2) 是 seg2，後面兩個是 drawPart 加的。

h8. 為什麼關節處要畫一顆球？（main.cpp:352、357）

兩節 capsule 轉出角度時，關節外側會出現縫隙或尖角。球心在關節原點，畫成稍粗於手臂的球（thick × 1.3 / × 1.2）把接縫蓋住，看起來像機械關節。

h9. drawLimb 回傳什麼？拿去做什麼？

回傳 seg2 · T(0, −len, 0)：前臂 / 小腿末端（手腕 / 腳踝）的矩陣，不含 scale。drawRobot 拿它畫手掌（球）和腳掌（Cube），所以手掌、腳掌是第三層子節點。

h10. 為什麼 glUniformMatrix4fv 的 transpose 參數是 GL_FALSE？glm::value_ptr 做什麼？

GLM 和 GLSL 都是 column-major，記憶體排列一致，不用轉置。value_ptr 回傳指向矩陣 16 個連續 float 第一個的指標，給 OpenGL 讀。

h11. 按 Q / E 轉身時，機器人繞哪一點轉？如果寫成先 rotate 再 translate 呢？

torso = T(位置) · Ry(yaw) → 繞自己身體中心的垂直軸原地轉。若寫成 Ry(yaw) · T(位置)，會繞 world 原點公轉；robotPos 不是 0 時機器人會繞圈移動。

h12. jointMatrix 的三個 rotate 順序換成 X→Y→Z，揮手動作會一樣嗎？

不一定。3D 旋轉不可交換，只有一個軸非 0 時順序無關；多軸同時非 0 時（例如 Walk 的 lArm1 = (0.5s, 0, −0.08)）結果會略有不同。這是 Euler angle 的特性。

機器人組裝

r1. 畫出你的階層圖，每個節點有哪些 drawPart？

Torso（root：身體、胸口板、骨盆）→ Head（脖子、頭、2 眼、天線、天線球）；→ L1/R1 Arm（肩球、上臂）→ L2/R2 Arm（肘球、前臂）→ 手掌；→ L1/R1 Leg（髖球、大腿）→ L2/R2 Leg（膝球、小腿）→ 腳掌。

r2. 每一幀有幾個 draw call（不含 ImGui）？大約多少頂點？

torso 3 + head 6 + 四肢各 4（2 球 + 2 capsule）× 4 = 16 + 手掌 2 + 腳掌 2 = 29 個 glDrawArrays。頂點：13 顆 Sphere × 2304 + 8 個 Capsule × 2496 + 6 個 Cube × 36 + 2 個 Cylinder × 240 ≈ 50,616，Sphere 佔六成。

r3. TORSO_HEIGHT = 2.26 怎麼來的？（main.cpp:84–85）

從 torso 中心往下：髖關節在 −0.7、大腿 0.7、小腿 0.7、腳掌高 0.16（中心在腳踝下 0.08）→ 0.7 + 1.4 + 0.16 = 2.26。torso 中心放在 y = 2.26，站直時腳底剛好在 y = 0。

r4. 頭的關節為什麼在 (0, 0.6, 0)？頭的中心為什麼在關節上方 0.4？

torso 的 scale y = 1.2，半高 0.6 → 脖子關節在 torso 頂面。頭的 Cube 高 0.5，中心放在 0.4 → 底面在 0.15，中間 0.15 是脖子（Cylinder，高 0.16）。頭繞脖子關節轉，不是繞頭中心轉。

r5. 陷阱 程式裡的 rArm（x = +0.7）是機器人自己的右手嗎？

不是。機器人面向 +z（朝相機），它自己的右手在 −x（觀眾的左邊）。程式的 L / R 是以觀眾畫面的左右命名。Demo 時講清楚即可：「L/R 是畫面左右」。

r6. 腳掌為什麼 offset 是 (0, -0.08, 0.08)？

腳掌 Cube 高 0.16，y 往下 0.08 → 頂面剛好在腳踝；z 往前（+z，機器人面向）0.08 → 腳尖往前伸，像真正的腳。

r7. 下半節為什麼是 color * 0.85f、thick * 0.9f？

前臂 / 小腿顏色暗一點、細一點，讓兩節分得出來，純視覺設計。glm::vec3 * float 是每個分量都乘。

r8. Sphere.obj 直徑 1，眼睛 glm::vec3(0.13f) 實際多大？會不會被頭擋住？

直徑 0.13。頭的 Cube 深 0.5 → 前表面 z = 0.25；眼睛中心在 z = 0.25，一半埋在頭裡、一半凸出來，depth test 只顯示凸出的半球。

動畫

a1. 暫停是怎麼做的？暫停時還能移動機器人嗎？

if (playing) animTime += dt;（main.cpp:565）：暫停 = 不累加，computePose 拿到同一個 t，姿勢就固定。processInput 不受 playing 影響，暫停時 WASD / QE / 拖曳仍然有效。

a2. computePose 有沒有記憶上一幀的狀態？切換動畫時會怎樣？

沒有，它只依 (mode, t) 算出姿勢（純函式）。所以切換 Combo 時姿勢會瞬間跳到新動畫的同一時間點，沒有過渡。要平滑可以記錄切換時刻，在一段時間內對兩個 Pose 做線性內插。

a3. Walk 一個步伐週期多久？擺幅幾度？

sin(t * 4) 週期 2π / 4 ≈ 1.57 秒。大腿擺幅 0.5 rad ≈ 28.6°，手臂同樣 0.5 rad。

a4. 角度正負代表什麼方向？用右手定則說明 x 負 = 往前擺。

繞 +x 軸、角度為正時，右手大拇指指 +x，四指從 +y 轉向 +z。腿原本指向 −y，正角度會讓它轉向 −z（往後）；負角度轉向 +z（往前，機器人面向 +z）。

a5. 陷阱 Walk 註解寫「往後擺的那隻腿膝蓋彎」，程式實際上是哪隻腿彎？（main.cpp:250–254）

s > 0 時 lLeg1.x = −0.5s 為負 → 左腿在前面，同時 lLeg2.x = 0.6·max(0, s) > 0 → 左膝彎。所以是「擺在前面的那隻腿膝蓋彎」，註解寫反了。小腿正角度 = 往後折，符合膝蓋方向。Demo 被問就照程式實際行為講，並說明註解有誤。

a6. std::max(0.0f, s) 在這裡的作用？

半波整流：只保留 sin 的正半週，負的部分變 0。用在膝蓋 / 手肘：關節只能往一個方向彎，一個週期內只在半週彎曲，另外半週伸直。

a7. Walk 時手和腳的相位關係？

左右腿反相（±0.5s）；手臂與同側的腳反相（lArm1.x = +0.5s vs lLeg1.x = −0.5s）→ 左腳在前時左手在後，跟人走路一樣。

a8. bodyY = 0.05 * |cos(4t)|：身體什麼時候最高？一個步伐週期彈幾次？

|cos| 最大時 sin = 0，也就是兩腿經過垂直、交錯的瞬間 → 身體最高（跟真實走路一樣）。|cos| 的週期是 cos 的一半，所以一個步伐週期（左右各一步）彈 2 次。

a9. Walk 的 head.y = −0.15s、torso.y = 0.1s，頭在 world 中實際轉多少？

head 是 torso 的子節點，角度是相對 torso。world 中頭的偏轉 = 0.1s − 0.15s = −0.05s，即頭的轉向和身體相反、幅度小，看起來像身體扭動時頭保持朝前。

a10. Wave 的 rArm1.z = 2.6 為什麼是繞 z 軸？2.6 是幾度？

z 軸指向機器人前方，繞 z 轉手臂會在左右平面（側舉）抬起。2.6 rad ≈ 149°：手臂從朝下（−y）轉到斜上外側。前臂 rArm2.z = 0.5·sin(6t) 左右揮。

a11. Jump 蹲下時 torso.x = 0.3·crouch，腿會不會跟著傾斜？

會。腿是 torso 的子節點，torso 前傾 0.3 rad，整雙腿也跟著轉 0.3 rad，腿的實際角度 = torso.x + leg1.x。若想讓腿不受身體傾斜影響，要在腿角度裡扣掉 torso.x，或改用骨盆當 root。

a12. Jump 蹲下時腳底會剛好貼地嗎？

不精確。bodyY = −0.35·crouch 是手調的近似值，沒有根據腿的角度反算（forward kinematics），腳可能稍微浮起或陷入（沒有畫地板所以不明顯）。精確做法：由大腿、小腿、torso 傾斜角算出腳踝高度，再決定 bodyY；或用 IK。

a13. 動畫為什麼用經過的時間，不是每幀 +1？

每幀 +1 的速度跟 FPS 綁在一起，換台電腦或關 vsync 速度就變。用 dt 累加，任何 FPS 下 1 秒就是 1 秒。

ImGui 與輸入

u1. ImGui 是 immediate mode GUI，這在 on_gui 怎麼看出來？

沒有建立 / 保存任何按鈕物件，每一幀都重新呼叫 Begin / Checkbox / Combo / End 描述 UI。Checkbox(&playing) 直接讀寫你的變數，使用者點了就在這一幀改掉 playing（回傳值為 true 表示這幀有改變）。

u2. ImGui::Combo("Animation", &animMode, modes, IM_ARRAYSIZE(modes)) 如何對應到 enum？

Combo 把選到的 index（0、1、2）寫進 animMode；字串陣列順序 Walk / Wave / Jump 與 enum { ANIM_WALK = 0, ANIM_WAVE = 1, ANIM_JUMP = 2 } 一致。IM_ARRAYSIZE = sizeof(arr) / sizeof(arr[0]) = 3。所以 animMode 宣告成 int 而不是 enum 型別。

u3. 為什麼自己的 callback 要在 ImGui_ImplGlfw_InitForOpenGL(window, true) 之前設定？

第二個參數 true = ImGui 安裝自己的 GLFW callback，並記住原本已註冊的 callback，在它處理完後串接呼叫。若之後才設定，glfwSet*Callback 會把 ImGui 的 callback 換掉 → ImGui 收不到滑鼠，選單點不動。

u4. 鍵盤用 glfwGetKey（polling），滑鼠用 callback，為什麼？

移動需要「按住就持續動」，每幀問一次按鍵狀態最直接，乘 dt 速度穩定。key callback 只在按下 / 放開 / repeat 時觸發，repeat 有延遲且頻率不固定。滑鼠拖曳需要「按下那一刻」記錄起點、每次游標移動的增量，用事件比較自然。單次觸發的動作（例如按 P 切換暫停）才適合 key callback。

u5. WantCaptureMouse 為什麼只在按下時檢查，放開時不檢查？（main.cpp:463–469）

按下時在 ImGui 視窗上 → 不開始拖曳。放開時不管在哪都要結束拖曳；若放開時也檢查，在場景按下、拖到選單上放開，dragging 會卡在 true，之後滑鼠一動機器人就轉。

u6. 陷阱 機器人面向相機時按 W，它往哪走？跟面向一致嗎？

robotPos.z -= move → 往 world −z（遠離相機、畫面深處）。機器人 yaw = 0 時面向 +z，所以 W 讓它倒退走；轉身後 WASD 方向也不跟著轉（是 world 軸向，不是機器人自己的前後）。題目只要求「控制位置與旋轉」，符合規定；改法見 x1。

u7. 移動速度是多少？為什麼乘 dt？

move = 2.0f * dt → 每秒 2 單位；turn = 2.0f * dt → 每秒 2 rad（約 115°）。不乘 dt 的話每幀固定移動量，FPS 高的電腦跑得比較快。

u8. 拖曳 1 個像素轉多少？為什麼不用乘 dt？

0.01 rad / 單位（約 0.57°）。滑鼠拖曳是「位移量」驅動，移了多少就轉多少，與經過時間無關；乘 dt 反而讓轉速跟 FPS 有關。（嚴格說游標座標是 screen 座標，HiDPI 下不等於像素。）

u9. 點過 ImGui 選單後，WASD 會不會失效？

不會。這份程式沒有開 ImGuiConfigFlags_NavEnableKeyboard（template 原本有，已拿掉），所以 WantCaptureKeyboard 只在有 ImGui 元件正被操作（ActiveId != 0，例如按住 Checkbox、正在文字框打字）或有 modal 視窗時為 true；點完放開就恢復。processInput 開頭的檢查只擋這段時間。

u10. 為什麼不能用 scanf / std::cin 讓使用者輸入？

作業規定（−10）。而且 console 輸入會阻塞主迴圈：等輸入時不會 poll events、不會重畫，視窗凍結。所有輸入都走 GLFW 事件 / ImGui。

綜合 / 規則

g1. 你的程式哪裡證明沒有用 fixed function pipeline？

沒有 glBegin / glVertex / glTranslatef / glPushMatrix / glMatrixMode；矩陣全部由 GLM 計算、用 glUniformMatrix4fv 傳給自己的 VS；頂點資料放在 VBO、由 VAO 描述；context 是 core profile（fixed function 在 core profile 根本不能用）。

g2. 程式結束時有釋放 VAO / VBO / texture / program 嗎？

沒有呼叫 glDeleteVertexArrays / glDeleteBuffers / glDeleteTextures / glDeleteProgram。glfwDestroyWindow 刪掉 context 時 driver 會一起回收，程式結束 OS 也會回收，所以沒有實際影響；嚴謹的寫法是在清理段補上。

g3. TINYOBJLOADER_IMPLEMENTATION、STB_IMAGE_IMPLEMENTATION 是什麼？為什麼只能定義一次？

header-only 函式庫：沒定義時 header 只有宣告；定義後 include 會把函式實作也展開進這個 .cpp。如果兩個 .cpp 都定義，同一個函式會有兩份定義 → link 時 multiple definition 錯誤。本作業只有 main.cpp，所以放這裡。

g4. 全域變數裡，哪些是「輸入寫、繪製讀」的狀態？

robotPos / robotYaw（processInput、滑鼠 callback 寫 → drawRobot 讀）、playing / animMode（ImGui 寫 → 主迴圈 / on_display 讀）、animTime（主迴圈寫 → computePose 讀）、dragging / lastMouseX（只在滑鼠 callback 之間使用）。

g5. 為什麼 Mesh 可以宣告成全域變數，在 GL context 建立之前就存在？

全域的 Mesh 只是三個整數（初始為 0），宣告時不呼叫任何 OpenGL 函式；真正建立 GPU 資源是在 GLAD 初始化之後呼叫 loadObj 時。
